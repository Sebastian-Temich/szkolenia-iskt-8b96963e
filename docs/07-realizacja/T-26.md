## Decyzje

- Które hasła testowe? → `Redaktor-lokalnie1` i `Bez-roli-lokalnie1`, przykład z issue i Z1
  specyfikacji (potwierdzone przez właściciela 2026-11-13); spełniają `lower_upper_letters_digits` i
  ≥ 8 znaków, a nazwy zostają rozpoznawalne względem starych.
- Jak sprawdzić W-10/K3 bez `curl` (poza profilem workera)? → skrypt `node` (komenda dozwolona) w
  katalogu tymczasowym sesji, poza repo, z lokalnym kluczem publishable z `shctl db status`; tokenów
  nie wypisywał.
- Czy sprawdzać, że stare hasła nie działają? → tak, osobna asercja pgTAP (6b): zmiana haseł to
  regresja dla istniejących instrukcji i testów E2E, więc test pilnuje, że nikt nie zostawił starego
  hasła w seedzie.
- Stare hasła w `docs/07-realizacja/T-8.md` i `docs/decyzje.md` → bez zmian: to zapis historyczny
  zadania T-8, a `decyzje.md` to plik wspólny (worker go nie edytuje).

## Drobne uwagi

- `shctl db` wypisuje „WARN: config section [inbucket] is deprecated … use [local_smtp]”, choć
  `supabase/config.toml` ma `[local_smtp]`; na serwerze działa Supabase CLI v2.121.0, a nagłówek
  `config.toml` mówi o szablonie z CLI 3.1.0. Ostrzeżenie pochodzi z kopii roboczej shctl
  (`/Users/Shared/sh/stan/db/szkolenia-iskt`), której worker nie może czytać.
- `docs/decyzje.md` (wpis T-8 z 2026-11-13) ma stare hasła testowe; orkiestrator może dopisać
  nowszą decyzję przy zamknięciu tego zadania.

## Ryzyka

- `pnpm build` i E2E sprawdzone tylko w CI (sandbox: `.env.local`, przeglądarki); oba zielone.
- Ostrzeżeń `db advisors` (WARN, INFO) z logu joba `baza` nie przeglądałem; PR nie zmienia schematu
  (tylko `[auth]` w config, seed i test), więc lista ostrzeżeń jest taka jak po #25.
- Każdy, kto ma lokalną bazę z poprzednim seedem, musi wykonać `shctl db reset`, żeby zalogować się
  nowymi hasłami (README, krok 2, opisuje reset).
- `site_url` dotyczy linków w e-mailach auth; ich treści lokalnie (Mailpit) nie sprawdzałem, bo
  rejestracja jest wyłączona, a zadanie nie dodaje przepływu z e-mailem. Kryterium K1 to przegląd pliku.

## Propozycje dla systemu

- Profil workera mógłby dopuszczać `curl` tylko do `http://127.0.0.1:<blok portów projektu>` (albo
  `shctl db` mógłby mieć komendę `shctl db login --email … --haslo …`), żeby kryterium „logowanie
  przez lokalne API” sprawdzać bez skryptu pomocniczego.
- `shctl db` mógłby wypisywać wersję Supabase CLI i ścieżkę kopii roboczej konfiguracji przy
  ostrzeżeniach konfiguracji, bo worker nie może czytać `/Users/Shared/sh/stan/db/`.
